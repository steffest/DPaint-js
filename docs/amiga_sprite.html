Amiga Sprite

DPaint.js can export images as Amiga hardware sprites.
A hardware sprite is a small image the Amiga custom chips draw on top of the playfield, without any CPU work. It is always 16 pixels wide and uses 2 bitplanes, which gives 4 color indices: index 0 is transparent, indices 1, 2 and 3 are the sprite colors.

Pick Amiga Sprite in the Save dialog. The Output option decides what gets written:

  • Show code: C source for one sprite, generated from the current frame. The result is shown in a dialog so you can copy/paste it into your project.
  • Binary file: a Sprite Bank file (.spr) that contains one sprite per animation frame, ready to be loaded straight into CHIP RAM.

Requirements

  • The image must be 16 pixels wide (narrower images are padded to the right).
  • Maximum height is 320 lines.
  • Maximum 4 colors, and they must be the first 4 colors of the palette: a sprite carries no palette of its own, its pixels are just indices 0-3. Colors outside those 4 entries are reported as an error instead of being silently dropped.
  • Transparent pixels become index 0.

If your palette has exactly 3 colors, DPaint.js adds the transparent entry in front of it, so the 3 colors become sprite colors 1, 2 and 3.

The hardware can also pair two sprites into a single 16 color one, see Attached sprites at the bottom of this page.

Show code

The generated array is the exact memory layout the hardware expects: two control words, then two data words per line (one for each bitplane), then two termination words. 

static UWORD __chip sprite[] = {
  0x0000, 0x0000,
  0x8000, 0x0000,
  0xc000, 0x4000,
  ...
  0x0000, 0x0000
};

The first two words hold the vertical start/stop position and are left at zero: fill them in at runtime (usually through a sprite_setPosition() style helper) before handing the pointer to the copper.

Sprite Bank file format (.spr)

The Sprite Bank stores several sprites in one file. The layout matches the memory layout the Amiga hardware needs, so loading is a plain file read into CHIP RAM: no parsing, no relocation, no conversion.

  • Extension: .spr
  • Endianness: big-endian (Motorola 68000)
  • Alignment: everything is 16-bit word aligned

Header

The header size depends on the number of sprites.

UWORD magic          /* 0x5350, ASCII "SP" */
UWORD numSprites     /* number of sprites in this bank */
ULONG offsets[numSprites]  /* byte offset of each sprite, from the start of the file */

The offsets are 32-bit, so a bank is not limited to 64KB. DPaint.js writes one sprite per animation frame, in frame order, so offsets[0] is frame 1.

Sprite data block

Every sprite is stored as a ready-to-use hardware sprite:

UWORD vstart_vstop_1   /* 0x0000, placeholder, overwritten when positioning the sprite */
UWORD vstart_vstop_2   /* 0x0000, placeholder */
UWORD data[height * 2] /* per line: bitplane 0 word, then bitplane 1 word */
UWORD end_1            /* 0x0000, hardware termination */
UWORD end_2            /* 0x0000, hardware termination */

Total size of one sprite is 2 + (height * 2) + 2 words. All sprites in a bank written by DPaint.js have the same height (the image height), but the offset table means a reader never has to assume that.

Example: a 3 line sprite bank with 2 sprites

offset  bytes        meaning
0000    53 50        magic "SP"
0002    00 02        2 sprites
0004    00 00 00 0C  sprite 0 starts at byte 12
0008    00 00 00 1A  sprite 1 starts at byte 26
000C    00 00 00 00  sprite 0: control words
0010    80 00 00 00  line 0: plane 0 = 0x8000, plane 1 = 0x0000
0014    40 00 C0 00  line 1
0018    00 00 00 00  line 2
001C    00 00 00 00  sprite 0: termination
...

Reading a sprite bank on the Amiga

Because the file needs no parsing, loading it is just a read into CHIP RAM plus a check on the magic number. 

struct SpriteBank {
    UWORD magic;
    UWORD numSprites;
    /* ULONG offsets[] follows immediately */
};

UWORD *getSpriteData(struct SpriteBank *bank, UWORD spriteIndex) {
    ULONG *offsets;
    if (!bank || bank->magic != 0x5350 || spriteIndex >= bank->numSprites) return 0;
    offsets = (ULONG *)((UBYTE *)bank + sizeof(struct SpriteBank));
    return (UWORD *)((UBYTE *)bank + offsets[spriteIndex]);
}

The returned pointer can be used directly as a sprite pointer: set its position, point the copper at it, done. Since each sprite is addressed through the offset table, sprites do not have to sit in fixed size blocks and variable height sprites work without any extra bookkeeping.

Attached sprites (16 colors)

DPaint.js does not export attached sprites yet: the exporter always writes 2 bitplane, 4 color sprites. This section describes what the hardware does, so the format can grow into it later.

The 8 hardware sprites are wired together in fixed pairs: 0+1, 2+3, 4+5 and 6+7. Normally each pair shares one set of 3 colors plus transparent:

Sprite pairColor registers used
0 and 117, 18, 19
2 and 321, 22, 23
4 and 525, 26, 27
6 and 729, 30, 31

Setting the attach bit on the odd sprite of a pair glues the two together into a single sprite that is still 16 pixels wide, but now has 4 bitplanes and therefore 16 color indices. Index 0 stays transparent, indices 1-15 map straight onto color registers 17-31, so an attached sprite has the whole upper half of the palette to itself instead of 3 colors.

Attaching costs you a sprite: a pair that would otherwise draw two independent 4 color objects now draws one 16 color object. The DMA cost is the same either way.

Bitplane order

The two sprites of the pair each supply 2 of the 4 bits per pixel:

  • the even sprite supplies bitplanes 0 and 1 (the low 2 bits of the color index)
  • the odd sprite supplies bitplanes 2 and 3 (the high 2 bits)

So a 16 color image is split over two completely normal sprite structures. Per line, the even sprite holds plane0, plane1 and the odd sprite holds plane2, plane3 for the same 16 pixels: 

pixel color index (0-15)  =  bit3 bit2 bit1 bit0
                              |    |    |    |
       odd sprite, word 2  ---+    |    |    |
       odd sprite, word 1  --------+    |    |
      even sprite, word 2  -------------+    |
      even sprite, word 1  ------------------+

The attach bit

The attach bit lives in the second control word (SPRxCTL) of the odd sprite of the pair: bit 7, so mask 0x0080. Setting it on the even sprite has no effect. Both sprites must be given the same vertical start/stop and the same horizontal position, otherwise the two halves drift apart and the result is a mess of unrelated colors. 

/* both sprites of the pair get the same position ... */
sprite_setPosition(spriteEven, x, y, height);
sprite_setPosition(spriteOdd,  x, y, height);

/* ... and the odd one gets the attach bit in its second control word */
spriteOdd[1] |= 0x0080;

How this would fit the sprite bank

Nothing in the .spr format blocks attached sprites: they are two ordinary sprite data blocks, so a pair is simply two consecutive entries in the bank (even first, odd second) and the loader sets the attach bit after loading. What is missing today is on the DPaint.js side: it would have to accept a 16 color, 16 pixel wide image, split it into 4 bitplanes, and write planes 0-1 and planes 2-3 as two separate sprites - plus a way to mark in the file which entries belong together.
